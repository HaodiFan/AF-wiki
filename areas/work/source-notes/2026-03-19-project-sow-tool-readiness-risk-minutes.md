# 2026-03-19 项目SOW与工具就绪风险 听记

## 核心内容摘要
### 1. 项目一开始就在错误假设上签了 SOW
- 最初签约默认“已有工具可以直接交付合格数据”。
- 真实情况是工具并不 ready，客户看到第一版产出后直接判定不可接受。
- 这意味着 SOW 的隐含前提不成立，后续所有交付压力都建立在错误基础上。

### 2. 客户需求没有真正对齐，验收标准持续漂移
- 客户没有在前期把需求想清楚，也没有和交付方完成有效对齐。
- 实际过程中“每天都有新的错法”，导致质量标准始终在变化。
- 初期只用 3 条样本做可行性验证，远远不足以暴露后期复杂问题。

### 3. 交付节奏被工具问题吞掉了
- 原定三个月周期里，有两个月实际上被工具迭代消耗掉。
- 客户体感会变成“你们没东西交”，即使团队实际上在等待工具成熟。
- 最后虽然项目被顺延半年，没有形成直接商务事故，但也没有因此获得额外补偿。

### 4. 最大效率黑洞是流程过长且工具断裂
- 数据链路大致是：标注 -> 质检 -> 判断重标还是修复 -> 执行修复。
- 一条数据最少要过四道人工。
- 质检一次可能耗费半天到两小时，修复又依赖单类错误对应单类方法。
- 本质问题是：录入工具有，修复工具没有；录和修被解耦，导致反复人工回路。

### 5. 本该优先做 V0 工具，却把它做成了产品化工程
- 后来做出的端到端修复工具花了四个月。
- 复盘认为这四个月里掺杂了“想把它做成产品”的 ego，而不是先做一个能救火的工具。
- 如果目标只是 V0、只是解决当下问题，按现在的 web coding 能力，可能一周到两周就能做出足够可用的版本。

### 6. 风险识别与复盘机制存在，但没有真正转化成行动
- 周会和复盘动作并不是没有，而是“盘了但没盘出来东西”。
- 没有快速识别出“哪个环节最重、最卡、最该工具化”。
- 对话里明确提出：如果人识别不出来，应该让 AI 帮忙做风险识别、流程拆解和工具优先级判断。

## 对未来项目的直接启发
### 1. SOW 必须写清楚“工具是否 ready”
SOW 不能只写交付结果，还要写清：
- 是否依赖现有工具
- 工具成熟度如何
- 哪部分属于前置准备
- 哪部分不在本项目范围内
- 如果工具不 ready，是否触发顺延 / 变更 / 加价

### 2. 首单或新领域项目要默认先跑最小闭环
比起一下子签完整大单，更合理的是：
- 先定义最小交付单元
- 先冻结最小验收标准
- 先用最小规模暴露错法分布
- 再决定是否扩大范围

### 3. 工具优先级要前置，而不是边交付边补
这次最大的教训不是“工具难做”，而是“工具建设排位太靠后”。
真正应该优先做的是：
- 能直接减少人工回路的工具
- 能在标注过程中即时发现问题的工具
- 能把录入和修复重新耦合起来的工具

### 4. V0 工具比产品化更重要
当下问题如果是交付会炸，优先级应该是：
- 先能用
- 先止血
- 先把最长路径砍掉
而不是先追求抽象、通用、产品化、可扩展。

### 5. AI 更适合做“项目风险扫描器”
听记里一个很强的洞见是：
- 如果人自己看不清项目范围和风险，可以让 AI 帮忙先做结构化识别。
- AI 可以帮助产出：
  - 项目范围
  - 最大风险
  - 时间瓶颈
  - 值得优先工具化的步骤
  - 哪些动作可以先手搓一个 V0 自动化

## 可沉淀成方法论的检查表
以后遇到类似项目，启动前至少要问：
- SOW 依赖的工具是否真的 ready？
- 客户是否真正参与并确认过验收标准？
- 是否存在“每天出现新错法”的高漂移风险？
- 交付链路里最长、最重、最耗时的人工步骤是哪一步？
- 有没有一个一周内能落地的 V0 工具先砍掉主瓶颈？
- 如果客户标准会变，合同里是否写了顺延 / 变更 / 额外报价机制？
